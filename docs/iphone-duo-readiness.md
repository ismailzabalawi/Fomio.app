# iPhone Duo preparation

Started 2026-10-18 (Asia/Amman). Focused Duo simulator reply continuity now passes; the wider native acceptance matrix remains open.

## Direction

Keep the tab bar with per-tab navigation, the adaptive reading split (one pane, list + discussion, then community sidebar) and the bounded reading column across compact and expanded windows. Pane count follows the width each tab root is offered, scaled for text size. Adapt to the space SwiftUI supplies rather than identifying a foldable device or using hinge angles as layout inputs. Preserve the selected tab, each tab's path, loaded discussion, writing, editor mode and selection through size changes. Keep the iOS 26 deployment target; building with a newer SDK is separate from raising the minimum OS.

Apple's [preparation guide](https://developer.apple.com/iphone-duo/prepare/) describes dynamic resizing with the iOS 27 SDK and edge-to-edge content with vertical system bars when linked against iOS 27.1 or later. Its [Duo HIG](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo) calls for safe-area-aware content and standard adapting system controls. Those new layouts require their own native validation before shipping a newly linked build.

**Resizability audit — 2026-10-20:** Apple's app-resizability checklist was run against the project and source. Build configuration passes all three prerequisites: a generated launch screen (`INFOPLIST_KEY_UILaunchScreen_Generation`), all four iPad orientations and no `UIRequiresFullScreen` key, in both `project.yml` and the committed project file. Production source contains no `UIScreen.main`, `interfaceOrientation`, `ignoresSafeArea` or UIKit app-delegate lifecycle, and no layout decision based on `userInterfaceIdiom`. One idiom check remains (corrected 2026-10-22): the feed options menu offers **New window** only when `UIDevice.current.userInterfaceIdiom == .pad` (`FeedView.optionsMenu`), so Duo never offers a second browsing window. This gates a feature, not geometry; replacing it with a multi-window capability check is open; fixed `.frame` values include touch targets, glyphs, bounded reading columns and media layouts; no inspected uses encode a known display size. One finding was fixed: live sign-in walked `UIApplication.shared.connectedScenes` for a key window to anchor `ASWebAuthenticationSession`. The sign-in sheet now reads its own hosting window through `PresentingWindowReader` and passes it as `signIn(anchor:)`, so the authorization sheet is anchored to the scene that asked for it as that scene resizes. Fixture sign-in ignores the anchor and unit tests still call `signIn()` without it. Not changed: the composer's `UIApplication.shared.sendAction(resignFirstResponder)` keyboard dismissal is not a geometry assumption; the UI tests' `UIDevice.current.userInterfaceIdiom == .phone` checks run in the test-runner process and only decide whether a rotation request is expected to change window geometry. Verification: the first build attempt failed because the Mac's startup volume had about 420 MiB free; after the owner freed space, Xcode's build database was left reporting a spurious `FomioUITests → Fomio` dependency cycle, resolved by deleting this project's DerivedData (the project file was unchanged apart from a test source). Build-for-testing then passed in Xcode with SDK 27.1. **On iPhone Duo / iOS 27.1 (simulator `5325EFBF`): the full unit bundle minus live-server tests passed 125 of 125, and the focused set of six sign-in/authorization unit tests plus the `testGuestSignInDoesNotPost` UI journey passed 7 of 7** (`/tmp/fomio-duo-unit.xcresult`, `/tmp/fomio-duo-signin.xcresult`, machine-local). This verifies the fixture sign-in path and that the sheet still presents and dismisses with the window reader attached; it does not exercise a live `ASWebAuthenticationSession` on Duo, which depends on the pending live-site authorization work.

## Initial source audit

| Area | Finding / action |
| --- | --- |
| Main-screen assumptions | No `UIScreen.main`, cached screen dimensions, device-size comparisons or orientation-based layout branches found in app source. |
| Global window lookup | Sign-in previously anchored the web authorization session to the first connected scene's key window. Replaced 2026-10-20 with the presenting sheet's own window (`PresentingWindowReader` → `AppState.signIn(anchor:)` → `AuthenticationService.signIn(anchor:)`). |
| Composer sheet | Replaced the iPad/phone idiom branch with `ComposerPresentationSizing`, based on the presenting shell's horizontal size class. Regular width delegates to system form sizing; compact/unspecified width delegates to page sizing. One `ComposerView` remains mounted as that value changes, preserving local editor/controller identity. |
| Navigation | `TabView` uses `.tabViewStyle(.tabBarOnly)`, not `sidebarAdaptable`. Each tab root owns its path and a `NavigationSplitView` (list / detail stacks split from the one path), and app-owned composer state remains. The app shell itself is not replaced at a width breakpoint. |
| Adaptive reading | `ReadingLayout` (`AdaptiveReadingLayout.swift`) reads the tab root's `GeometryReader` width: two panes at ≥ 720 pt (list 300 + discussion 420), plus the 260 pt `CommunitySidebar` at ≥ 1080 pt, all multiplied by a text-size scale (×1.15 at 23 pt body, ×1.6 at 34 pt). The reader can focus the discussion (detail only) or hide the sidebar. While the sidebar shows, the tab bar is hidden and the sidebar's tab rows replace it, including the Notifications unread badge (added 2026-10-22; build-verified only, no native or UI-test check yet). The split receives a `horizontalSizeClass` override (`.regular` when two panes fit, else `.compact`), so views inside it — e.g. `CommunityScopePicker` choosing popover vs sheet, and sheets presented from the split — see the layout's class rather than the window's. The composer sheet is presented from `AppShell`, outside the override, and keeps real window traits. Whether presented sheets inherit the override on Duo is unverified. |
| Reading column | Existing `ReadingColumn` caps text at 620 points while allowing narrower proposals. This cap is a reading measure, not an assumed display width. |
| Formatting | Existing `ViewThatFits` offers narrower rows. Regular width enables additional tools without assuming it means iPad. The custom bottom bar still needs Duo safe-area/keyboard checks. |
| Native editor | `sizeThatFits` uses the current width proposal, resizes attachments and invalidates TextKit layout when needed. Duo fixture folding now verifies text, caret/selection, focus and editor identity; attachment behavior remains unverified. |
| Build configuration | iPhone and iPad families and portrait/landscape are enabled; no `UIRequiresFullScreen` opt-out found. No change to version/build, signing, deployment target or distribution state in this pass. |
| Discourse | No adapter, permission or posting contract changes in this pass. |

Fomio iOS — IA & Wireframes

Low-fidelity, clickable wireframe pack for a native SwiftUI iPhone/iPad client backed by Discourse. Community = category, subcommunity = child category, discussion = topic, opening post and replies = posts. Discourse is authoritative for data, permissions, tracking/watching, validation and moderation. Labels "community", "discussion", "reply" and "Me" are working labels.

2Established vs. assumption vs. unresolved
ESTABLISHED
  • Four destinations: Home, Communities, Notifications, Me; global Search; Create is an action
  • Discourse categories/topics/posts; no Join or membership model, no recommendations
  • Guests browse Home, Communities, Search where site allows
  • Member-only actions authenticate, restore intent, recheck permission, never auto-post
  • One composer for Create/Reply/Quote/Edit/Resume, six independent state axes
  • Tracked is a separate Home filter; never active with unfiltered results
  • Tracking vs Watching = Discourse notification levels
  • Restricted cue only from Discourse data; no inferred Public/Private
  • Exact links keep topic ID and post number distinct
  • Local save never labeled as server-saved; pending ≠ published
  • No follower counts, chat, AI, paywall, interest picker or Explore
PROTOTYPE ASSUMPTIONS
  • Latest as initial Home sort (H01g)
  • Search and + Create in each tab's nav bar
  • Chronological replies as the D01 baseline
  • Full-screen composer on iPhone; sheet on iPad (IP02)
  • iPad: sidebar + list + detail (IP01)
  • All five notification levels exposed (CO02n)
  • Post disabled while uploads are in flight
  • Ineligible destinations shown disabled with reason
  • Read cache available offline (OF01)
  • Device settings reachable as guest
  • Illustrative content, usernames and IDs are fictional

5Technical verification notes (annotation layer only)
  • No deployment URL, credentials, API availability or enabled plugins are assumed. Every CONDITIONAL element needs a source field or capability check identified before build.
  • Verify per-post like/bookmark/reply/edit permission fields before showing actions on cards or posts.
  • Verify whether Hot and Tracked can be combined server-side; verify nested-reply data availability for the native client.
  • Verify draft endpoints and their sequencing semantics before labeling anything "saved to your account".
  • Verify whether and how Discourse signals a reply or edit queued for review. Until then the C17 inline card, who sees it, its persistence, and C16e edit-review handling are unverified prototype proposals; only "pending is not published" is established.
  • A not-found reconciliation check (CU02) is shown as unconfirmed, never as failed. Retry is explicit and warned; no idempotency or duplicate cleanup is promised.
  • Guest and member frames are kept separate: guest links stay on guest frames (H01g, CO02, CO02pg, D01), member links go to member frames (Home stack: H01m, CO02h, CO02hp, D01m; Communities stack: CO01, CO02m, CO02s, D01s). Each sign-in gate restores its own action (A2, A3).
  • This is a linked frame board. Static frames can't carry the stored intent, origin tab or back stack; where a generic frame is reused, the link is annotated SAMPLE-ONLY. Nothing here proves editable inputs, tab-stack persistence, draft recovery or device accessibility.
  • Define how a post number resolves to a post when posts are deleted or hidden (LK02).
  • Accessibility, RTL, split-view and device checks on the acceptance page are requirements; none have been tested.
